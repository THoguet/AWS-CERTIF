## Caching strategies

| Strategy | How | Pros | Cons |
|---|---|---|---|
| **Lazy loading / cache-aside** | Read the cache. On a **miss**, read the DB and populate the cache | Only requested data is cached. A cache failure is not fatal | Miss penalty (3 trips). **Stale data** until expiry or invalidation |
| **Write-through** | On every write, update the DB **and** the cache | Cache always fresh for written keys | Write penalty. Caches data that may never be read (churn) |
| **TTL** | Every entry expires after N seconds | Bounds staleness, frees memory | Too short → many misses. Too long → stale data |
| **Invalidate on write** | Write the DB, **delete** the cache key | Simple, fresh on next read | Next read is a miss |
| **Read-through** | The cache library/service loads from the DB itself on a miss (DAX behaves like this for DynamoDB) | Simpler application code | Needs a cache that knows your DB |

```python
def get_product(product_id):                      # lazy loading + TTL (exercise cache_1)
    key = f"product:{product_id}"
    value = cache.get(key)
    if value is None:
        value = db.load(product_id)
        if value is not None:
            cache.set(key, value, ex=300)         # TTL bounds staleness
    return value
```

> **Exam tip** — Real systems combine **lazy loading + write-through + TTL**. "Users sometimes see
> outdated data after an update" with lazy loading → add write-through or invalidation, or lower the TTL.

**Thundering herd / cache stampede**: when a popular key expires, many clients miss at once and hit
the database. Mitigations: jittered TTLs, request coalescing, pre-warming.

## Amazon ElastiCache

A managed in-memory cache in your VPC, with engines **Redis OSS**, **Valkey** (the open-source Redis
fork) and **Memcached**.

| | Redis OSS / Valkey | Memcached |
|---|---|---|
| Data structures | Strings, hashes, lists, sets, **sorted sets** (leaderboards), streams, geo | Simple key/value strings |
| Replication / HA | Replicas, **Multi-AZ with automatic failover** | No replication (data lost if a node fails) |
| Persistence / backups | Snapshots, AOF | None |
| Scaling | Cluster mode (sharding) + replicas | Multi-threaded, add nodes (client-side sharding) |
| Extras | Pub/sub, Lua, transactions, TTL per key | Simplicity |

Typical uses: database query cache, **session store** for stateless web servers, leaderboards
(sorted sets), rate limiting, pub/sub. Access requires network reachability (same VPC, security
group). A Lambda function using ElastiCache must be attached to the VPC. Security: in-transit TLS,
at-rest encryption, Redis AUTH / RBAC with IAM authentication.

**ElastiCache Serverless** removes capacity planning. **Amazon MemoryDB** is a Redis/Valkey-compatible,
**durable** in-memory **database** (multi-AZ transaction log): use it when the in-memory store is the
system of record, not just a cache.

> **Exam tip** — "Store user sessions so any instance behind the load balancer can serve the user"
> → **ElastiCache** (or DynamoDB) instead of sticky sessions. "Leaderboard / ranking in real time"
> → **Redis sorted sets**.

## Relational databases: RDS and Aurora

- **Amazon RDS** engines: MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Db2. **Aurora** is AWS's
  MySQL/PostgreSQL-compatible engine: storage replicated 6 ways across 3 AZs, up to 15 low-latency
  replicas, fast failover, **Aurora Serverless v2** (scales capacity automatically), Global Database.
- **Multi-AZ**: a **synchronous standby** in another AZ for high availability and automatic failover.
  You connect through the same DNS endpoint. It is not for read scaling (with the classic one-standby setup).
- **Read replicas**: **asynchronous** copies for **read scaling** (and cross-Region DR). Your app
  must send reads to the replica endpoint (Aurora has a reader endpoint), and replica reads may be slightly stale.
- **RDS Proxy**: a managed connection pool in front of RDS/Aurora. Essential for **Lambda**, where
  hundreds of concurrent functions would otherwise exhaust database connections. It also speeds up
  failover and can enforce IAM authentication.
- **IAM database authentication** (MySQL/PostgreSQL): connect with a short-lived token generated by
  the SDK (`generate_db_auth_token`) instead of a password.
- Credentials: store them in **Secrets Manager** with automatic rotation (chapter 14).
- Encryption at rest with KMS must be chosen **at creation**. To encrypt an existing unencrypted DB:
  snapshot → copy the snapshot with encryption → restore.

> **Exam tip** — "Lambda functions exhaust database connections during traffic spikes" → **RDS Proxy**.
> "Read-heavy app, the database CPU is saturated by reads" → **read replicas** (or a cache).
> "Survive an AZ failure with automatic failover" → **Multi-AZ**.

## Amazon CloudFront

A global **CDN** caching content at hundreds of edge locations, also used to accelerate dynamic
content and to protect origins.

- **Origins**: S3 buckets, ALB/EC2, API Gateway, Lambda function URLs, any HTTP server. **Origin groups** for failover.
- **Cache behaviors**: path patterns (`/static/*`, `/api/*`) route to origins with different cache settings.
- **Cache policy** = what goes into the **cache key** (selected headers, cookies, query strings) + TTLs.
  **Origin request policy** = what is forwarded to the origin **without** being part of the cache key.
  Every extra key element divides the hit ratio. Never add `User-Agent` or tracking parameters to the
  key unless the response really varies on them (exercise `opt_2`).
- TTLs: the origin's `Cache-Control: max-age` / `Expires` headers, bounded by the policy's min/default/max TTL.
- **Invalidations** (`/images/*`) remove objects before expiry (they cost money beyond the free quota).
  Prefer **versioned file names** (`app.3f2a1c.js`) for deployments.
- **Origin Access Control (OAC)** (successor of OAI): the S3 bucket stays private and its bucket
  policy only allows the CloudFront distribution. OAC also supports SSE-KMS buckets.
- HTTPS with **ACM certificates in us-east-1**. Field-level encryption, **geo restriction**, **AWS WAF**, Shield.

### Signed URLs and signed cookies

Restrict content to paying users (private content):

| | Signed URL | Signed cookies |
|---|---|---|
| Grants | **One** file | **Many** files (a whole video stream, a premium area) |
| Client | Any (also non-browser) | Browsers / clients keeping cookies |

Policies: **canned** (expiry only) or **custom** (start time, expiry, IP range). Signed with a
private key whose public key is in a **trusted key group** (exercise `cache_3`).

> **Trap** — CloudFront signed URLs ≠ S3 presigned URLs. With CloudFront in front of a private
> bucket, use **CloudFront** signed URLs/cookies. S3 presigned URLs go to S3 directly with IAM credentials.

### Code at the edge

| | **CloudFront Functions** | **Lambda@Edge** |
|---|---|---|
| Runtime | JavaScript, sub-millisecond, very cheap | Node.js / Python, up to seconds |
| Triggers | Viewer request / viewer response | Viewer **and origin** request/response |
| Network / body access | No network calls, no body access | Network calls allowed, body access |
| Use cases | Header manipulation, URL rewrites/redirects, simple auth (token check), A/B cookie | Auth with external calls, dynamic origin selection, image transformation, SEO rendering |

Lambda@Edge functions are created in **us-east-1** and replicated globally.

## Other data stores you should recognize

| Service | Use |
|---|---|
| **Amazon OpenSearch Service** | Full-text search, log analytics, dashboards. Often fed from DynamoDB Streams or Firehose |
| **Amazon Athena** | Serverless SQL queries directly on S3 (CSV, JSON, **Parquet**), pay per TB scanned. Partition and compress data to cut cost |
| **Amazon EFS** | Shared POSIX file system (NFS) across AZs. Mountable by EC2, ECS, **Lambda** (shared files, large ML models) |
| **Amazon EBS** | Block storage for one EC2 instance in one AZ (gp3, io2...) |
| **Lambda `/tmp`** | Ephemeral scratch space for one execution environment |

> **Exam tip** — Ephemeral vs persistent storage: `/tmp`, instance store and caches are **ephemeral**.
> S3, EFS, EBS, DynamoDB and RDS are **persistent**. "Several Lambda functions must share files" → **EFS** (or S3).

## Summary

- Lazy loading caches on demand (stale risk). Write-through keeps the cache fresh (write cost). TTL bounds staleness. Combine them.
- Redis/Valkey: data structures, replication, persistence, sessions, leaderboards. Memcached: simple, multi-threaded, no HA. MemoryDB: durable.
- RDS Multi-AZ = HA (sync standby). Read replicas = read scaling (async). RDS Proxy = connection pooling for Lambda.
- CloudFront: the cache key is in the cache policy, OAC keeps S3 private, signed URLs (one file) vs cookies (many), CloudFront Functions vs Lambda@Edge.
